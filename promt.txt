Prompt para Claude Code — Integração Conecta ↔ Intranet (SharePoint/Microsoft Graph)
Contexto do projeto

O Conecta é uma plataforma de recrutamento construída em React (frontend) com backend próprio. O sistema já possui:

Autenticação de usuários via Microsoft (Client ID e Client Secret já configurados e funcionando para login).
Uma integração existente com uma intranet do RH, incluindo uso do OneDrive dela.
Uma aba de configuração de ambiente relacionada a essa intranet, que já existe no sistema mas precisa ser expandida.

Antes de qualquer implementação, explore o repositório para entender:

Onde está a aba/tela de configuração de ambiente da intranet hoje (arquivo de frontend e, se existir, model/schema de backend associado).
Como a autenticação Microsoft atual está implementada (fluxo, biblioteca usada, onde ficam armazenados client_id/secret hoje — variável de ambiente, banco, key vault etc.).
Como a integração atual com o OneDrive/intranet do RH funciona (para reaproveitar padrões de chamada ao Microsoft Graph, se já existirem).
A estrutura de rotas de backend e o padrão de autorização por papel de usuário (admin/RH vs colaborador comum) já usado no projeto.

Não presuma nomes de arquivos ou pastas — descubra a estrutura real antes de escrever código. Siga os padrões de nomenclatura, estilo de código e organização de pastas já existentes no projeto.

Objetivo desta tarefa

Implementar a base de um "Mural de publicações" dentro do Conecta, onde admins/RH podem criar publicações (texto, foto) que são gravadas diretamente numa lista do SharePoint da intranet, via Microsoft Graph API — sem necessidade de endpoint público próprio, sem polling, sem sistema de fila.

Escopo desta etapa: uma intranet configurada por vez, mas a modelagem de dados e o código devem já estar preparados para múltiplos ambientes/intranets no futuro (não é para implementar seleção múltipla ou publicação simultânea em vários destinos agora — só não pode ser algo que exija reescrever tudo quando isso for adicionado).

Parte 1 — Expandir a aba de configuração de ambiente da intranet

Localize a tela/aba de configuração de ambiente da intranet já existente no Conecta e expanda-a para incluir todos os campos necessários para a conexão com o SharePoint via Microsoft Graph:

nome_ambiente (texto, nome amigável, ex: "Intranet RH Central")
tenant_id (texto)
client_id (texto) — se o Conecta já tiver um client_id/secret únicos usados para login, permita que este campo seja reaproveitado desse valor OU sobrescrito com um valor específico para este ambiente. Pergunte ao usuário via comentário no código ou levante a dúvida se não estiver claro qual comportamento faz mais sentido dado o que já existe.
client_secret (texto, sensível — deve ser armazenado de forma criptografada, nunca em texto puro; siga o padrão de segredos já usado no projeto para outras credenciais, se existir; caso não exista, use uma biblioteca de criptografia simétrica padrão e documente a variável de ambiente com a chave de criptografia)
sharepoint_site_url (texto, ex: "https://empresa.sharepoint.com/sites/RH")
site_id (texto — pode ser preenchido manualmente ou, idealmente, incluir um botão "Buscar site_id" que chama o Graph (GET /sites/{hostname}:/sites/{caminho}) usando as credenciais já preenchidas no formulário, e auto-preenche o campo)
list_id ou list_name (texto — mesma lógica: idealmente um botão "Buscar listas disponíveis" que lista as listas do site via Graph e permite selecionar de um dropdown)
ativo (boolean — permite desativar um ambiente sem excluí-lo)
status_conexao (calculado/exibido, não editável — resultado do último teste de conexão: sucesso, falha, nunca testado)

Adicione um botão "Testar conexão" nesta tela que:

Executa o Client Credentials Flow com as credenciais preenchidas.
Faz uma chamada simples ao Graph (ex: GET /sites/{site_id}) para confirmar que o token funciona e o site é acessível.
Exibe sucesso ou o erro retornado pela Microsoft de forma legível (ex: traduzir erros comuns como permissão ausente, admin consent pendente, client_secret expirado).
Atualiza o campo status_conexao.

Modele isso como uma nova entidade/tabela caso a aba atual seja apenas de configuração simples (chave-valor) e não suporte múltiplos ambientes ainda. Se a estrutura atual já for uma lista de ambientes, apenas adicione os campos novos ao modelo existente.

Parte 2 — Backend: publicação via Microsoft Graph

Implemente no backend:

Modelo de dados de publicações (publicacoes ou nome equivalente ao padrão do projeto):
id, titulo, texto, autor_id, status (rascunho / publicado / arquivado), data_publicacao, data_criacao, ambiente_intranet_id (referência ao ambiente configurado na Parte 1), sharepoint_item_id (guarda o ID do item criado no SharePoint, para permitir edição/exclusão futura), foto_url (ou tabela relacionada publicacao_fotos se houver mais de uma foto por publicação).
Função de autenticação Graph reutilizável: recebe tenant_id, client_id, client_secret como parâmetros (não fixos no código) e retorna um access token via Client Credentials Flow (POST https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token, grant_type=client_credentials, scope=https://graph.microsoft.com/.default). Trate cache de token com expiração para evitar autenticar a cada chamada.
Função de upload de foto: sobe a imagem para uma biblioteca de documentos do SharePoint (POST /sites/{site-id}/drive/root:/Publicacoes/{nome-arquivo}:/content) e retorna a URL do arquivo.
Função de criação de item na lista: POST /sites/{site-id}/lists/{list-id}/items com os campos da publicação. Deve buscar as credenciais e IDs do ambiente configurado (Parte 1) em vez de valores fixos.
Endpoint de publicação (ex: POST /api/publicacoes): recebe os dados da publicação vindos do frontend, salva no banco local com status apropriado, chama a função de upload de foto (se houver) e a função de criação de item na lista, salva o sharepoint_item_id retornado, e trata erros de forma que uma falha na chamada ao Graph não deixe o registro local em estado inconsistente (ex: salvar como "falha_publicacao" e permitir reprocessar).
Restrinja esse endpoint e os de gestão de publicações (criar/editar/despublicar) ao papel de admin/RH, seguindo o padrão de autorização já usado no projeto.
Parte 3 — Frontend: tela de mural

Crie ou adapte a tela de "Mural" dentro do Conecta, visível para admins/RH, com:

Lista das publicações existentes (com status: rascunho, publicado, falha de publicação, arquivado).
Botão "Nova publicação" abrindo um formulário com: título, texto (editor simples, pode ser rich text se o projeto já tiver algum componente desse tipo), upload de foto, seleção do ambiente de intranet configurado (dropdown vindo da Parte 1 — nesta etapa, normalmente um único ambiente ativo, mas o campo já deve existir para o futuro).
Botão "Publicar" que chama o endpoint da Parte 2.
Indicação visual clara de sucesso/falha da publicação no SharePoint (não apenas "salvo no Conecta", mas "publicado na intranet" vs "erro ao publicar na intranet: [motivo]").
Opção de tentar publicar novamente uma publicação que falhou.
Requisitos não funcionais
Nunca logar ou expor client_secret em logs, respostas de API ou no frontend após salvo (mostrar mascarado, ex: ••••••1234, e permitir apenas substituição, não visualização do valor salvo).
Todas as chamadas ao Microsoft Graph devem ter tratamento de erro específico para: credencial inválida, admin consent pendente (erro 403 típico), site/lista não encontrados, token expirado.
Documente no README (ou onde o projeto já documenta configuração) os passos que precisam ser feitos manualmente no Azure Portal antes desta funcionalidade funcionar: registrar/ajustar o App Registration com a permissão Sites.ReadWrite.All (Application permission) e obter admin consent do tenant.
Escreva testes (seguindo o framework de testes já usado no projeto, se houver) pelo menos para: a função de obtenção de token, a função de criação de item na lista (mockando a chamada HTTP), e o endpoint de publicação (casos de sucesso e de falha na chamada ao Graph).
